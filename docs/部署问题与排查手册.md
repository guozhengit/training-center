按严重度排序，每条含：现象 → 定位手法 → 根因 → 修复 → 预防。

## P0-1 新镜像在容器里根本起不来（日志路径写死 /var/log）

**现象**：镜像构建成功，本地 `docker run` 后立刻 `Exited (1)`，日志首行：

```
Logging system failed to initialize using configuration from 'null'
ERROR in RollingFileAppender[FILE] - Failed to create parent directories for [/var/log/training-center/app.log]
java.io.FileNotFoundException: /var/log/training-center/app.log (No such file or directory)
```

**定位**：本地起容器冒烟（`docker run -d -p 18080:8080 <tag>` + `curl /api/health`）+ `docker logs`。

**根因**：本次新增的 `logback-spring.xml` 把 `app.log`/`diag.log` 写到 `/var/log/training-center`，而容器以 **uid 1000** 运行，`/var/log` 属 root 且不可写。
**Windows 本地却完全正常**——`/var/log/training-center` 被解析成 `D:\var\log\training-center` 并自动创建，所以本地开发 100% 看不出来。

**修复**：改为**相对工作区根**的路径（容器内 CWD=`/workspace`，且该目录已 chown 给 uid 1000、生产还是 bind mount 会持久化）：

```xml
<file>output/training-runtime/logs/app.log</file>
<fileNamePattern>output/training-runtime/logs/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
```

顺带把同类硬编码一并改掉：`OpsService.LOG_ROOTS`（日志检索白名单）、`DiagnosticService.heapDump()`（堆转储落盘）。

**预防**：**镜像上传前必须先本地起容器冒烟**。凡是写路径，一律用相对工作区根的写法，不写 `/var/log` 这类需要 root 的绝对路径。

## P0-2 线上只有"写操作" 403：CORS 白名单不含生产域名

**现象**：浏览器 `POST https://train.sageflow.online/api/training/sessions` 403；但页面能打开、题库能加载；curl 直连 8080 / 9091 / 走域名**全是 200**。

**定位（关键手法）**：带上浏览器才会发的头复现——

```bash
curl -X POST -H 'Content-Type: application/json' \
     -H 'Origin: https://train.sageflow.online' -d '{...}' http://127.0.0.1:9091/api/training/sessions
# → 403
curl ... -H 'Origin: http://localhost:5173' ...
# → 200 + Access-Control-Allow-Origin: http://localhost:5173
```

一次就锁死是 CORS。

**根因**（两层叠加）：
1. `WebCorsConfig` 的 `allowedOriginPatterns` 写死为 `http://localhost:5173 / http://127.0.0.1:5173 / http://192.168.*.*:5173`，生产域名不在白名单；
2. 浏览器**同域 POST 也带 `Origin` 头**（GET 不带），而请求经 nginx 反代后容器内看到的是 `http`、Origin 是 `https` → scheme 不一致 → Spring 判为跨域 → 403。

所以表现是"页面正常、一点抽题就 403"。而且这**不是本次更新引入的**——线上所有 POST（含运行、提交判题）一直被拦，只是随机抽题是刚接上的功能才首次暴露。

**修复**：`WebCorsConfig` 改为读 `training.cors.allowed-origins`（默认保留开发域，逗号分隔、支持通配），方法补 `PATCH/DELETE`；生产 `docker-compose.prod.yml` 加：

```yaml
TRAINING_CORS_ALLOWED_ORIGINS: ${TRAINING_CORS_ALLOWED_ORIGINS:-https://train.sageflow.online,http://120.48.23.3:9091}
```

**预防**：验证线上接口**必须带 `-H 'Origin: <真实域名>'`**，不带 Origin 永远 200，会误判成正常。

## P1-1 compose 文件 YAML 缩进坏，部署止步 Step 5

**现象**：`first-deploy.sh` 跑到 `Step 5/6 启动容器` 报：

```
yaml: line 8: mapping values are not allowed in this context
```

**定位**：`sed -n '1,14p'` 看服务端 `deploy/docker-compose.yml`，第 7~11 行：

```yaml
    build:
    context: ../..
      dockerfile: training-center/Dockerfile   # ← 比 context 多缩进，非法
```

**修复**：`build:` 块整体缩进对齐。改完**先本地校验**再部署：

```bash
docker compose -f deploy/docker-compose.yml -f deploy/linux/docker-compose.prod.yml config -q
```

**注意**：`docker-compose.prod.yml` 的 `environment` 是**映射写法**，不能混入 `- KEY=VALUE` 列表项（会直接 YAML 报错）——本次修 CORS 时差点又踩一次。

**附带结论**：compose 语法错发生在 Step 5，**旧容器仍在健康运行，线上服务没有中断**。这一点值得记住：部署失败≠服务挂了。

## P1-2 构建上下文不能用父目录

**现象/风险**：构建上下文需要是 `training-center` 的**父目录**（Dockerfile 里写的是 `COPY training-center/...`），而 `D:\AI-SOURCE` 下有 28 个兄弟项目、且没有 `.dockerignore` → 会把几十 GB 全量上传给 Docker。

**处理**：手工造干净上下文 `_buildctx/`（只放精简后的 `training-center/` + `_fe/dist`，约 125MB），在里面跑 buildx。详见[服务器部署指南](服务器部署指南.md)第 3 节。

## P2-1 `first-deploy.sh` 归档名硬编码旧 tag

脚本里默认写死 `training-center-20260914-fix2.tar.gz`。**不用改仓库**，用环境变量覆盖即可：

```bash
IMAGE_ARCHIVE=/home/docker/training-center-20261008-fix2.tar.gz \
SRC_ARCHIVE=/home/docker/training-center-src-20261008-fix2.tar.gz \
TRAINING_PORT=9091 bash first-deploy.sh
```

后续更新可直接跳过它，走 `docker load` + `deploy.sh --image <tag>`（更快，省一次镜像导入）。

## P2-2 Docker Hub 不通

不能用 `DOCKER_BUILDKIT=1 docker build`（会去拉 `moby/buildkit`），必须：

```bash
docker buildx build --builder desktop-linux --load ...
```

## P2-3 Maven 不能加 `-o`

本地 `.m2` 缺 `spring-boot-dependencies`，离线构建会失败。构建必须联网（阿里云镜像可达）。

## P2-4 新建 `.ps1` 必须是 UTF-8 BOM

否则 PowerShell 5.1 按 GBK 解析，中文直接乱码到语法报错。

## P2-5 sha256 要算**压缩后**的归档

校验值必须基于 `training-center-<tag>.tar.gz`（gzip 之后），不是 `docker save` 出来的原始 tar。上传后在服务器再算一次比对。

## P2-6 归档体积

镜像归档约 **436MB**（Docker 层本身已压缩，`gzip -9` 几乎压不动），scp 上传约 6 分钟；传完记得在服务器 `rm -f` 释放空间。

## P3 其它已知坑（历史积累）

| 坑 | 说明 |
|---|---|
| 容器 uid 1000 | 可写目录必须 chown 1000；新增写路径时注意 |
| Redis ACL | 192.168.1.160 的 Redis 开了 ACL，`default` 已禁用，必须带用户名 |
| Lettuce `CLIENT SETINFO` | ACL 用户无 `client\|setinfo` 权限时连接被中止；已在 `RedisConnectionConfig` 里通过自建 `RedisURI` + `setLibraryName(null)/setLibraryVersion(null)` 根治 |
| Windows jar 文件锁 | `mvn clean` 前必须先停掉运行中的 java 进程 |
| curl 走系统代理 | 本地测接口加 `--noproxy '*'`，否则 502 |
| Vue prop 未 `.value` | 传 Ref 对象给子组件 → 整页白屏 |
| 服务器端口冲突 | 9090 已被 typing-game 占用，故用 9091 |
| 内存紧张 | 整机 1.9G，容器限 1G、堆 256m，**只能单路判题，勿并发** |

## 排查工具箱

```bash
# 1) 分层对比，快速判断是应用还是代理的问题
curl -s -o /dev/null -w '%{http_code}\n' -X POST ... http://127.0.0.1:9091/api/...      # 直连宿主机端口
docker exec training-center sh -c "curl -s -o /dev/null -w '%{http_code}\n' -X POST ... http://localhost:8080/api/..."  # 容器内
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Origin: <域名>' ... https://<域名>/api/...   # 模拟浏览器

# 2) 看真实错误
docker logs --tail 100 training-center

# 3) compose 语法
docker compose -f deploy/docker-compose.yml -f deploy/linux/docker-compose.prod.yml config -q

# 4) 数据是否完好
docker exec training-center python3 -c "import sqlite3;c=sqlite3.connect('/workspace/output/training-runtime/database/training.db');print([(t,c.execute(f'select count(*) from {t}').fetchone()[0]) for t in ['attempts','sessions','judgements']])"

# 5) 镜像上传前本地冒烟（必做）
docker run -d --name tc-smoke -p 18080:8080 <tag>
curl --noproxy '*' -s http://localhost:18080/api/health
```
