# Interview Training Center：面试项目介绍

> 适用场景：Java 后端、AI 应用/AI Agent 工程师、全栈工程师岗位面试。本文基于当前项目实现整理；涉及“效率提升”等结果，可按真实使用数据替换。

## 1. 项目概述

**Interview Training Center** 是一个面向开发者的本地化结构化面试训练系统，服务于机试题、口述题和项目答辩三类训练场景。它要解决的不是“缺题”，而是传统刷题过程中题目来源分散、训练过程不可追溯、完成后缺少复盘和下一步计划的问题。

我将训练过程沉淀为可查询的数据资产，并用统一题库、限时会话、自动判题、历史记录、错题复习和导出报告，形成以下学习闭环：

```text
目标岗位/能力诊断 → 选择题目 → 限时训练 → 提交与判题 → 训练报告
      ↑                                                   ↓
      └──────────── 错题队列与复习计划 ← 历史数据分析 ────┘
```

系统采用 Java 17 + Maven 多模块后端、Spring Boot Web API、Vue 3 前端与 SQLite 本地数据库，既支持命令行离线训练，也支持浏览器中的可视化训练面板。

## 2. 我的核心贡献

### 2.1 技术架构与模块解耦

采用 Maven 多模块架构，将业务领域能力与交互入口拆分：

| 模块 | 职责 | 设计价值 |
| --- | --- | --- |
| `training-core` | 题库加载、领域模型、SQLite 持久化、复习队列、代码沙箱与判题 Runner | 将核心训练能力从 UI 和接口层中抽离，保证 CLI 与 Web 共用同一套规则 |
| `training-cli` | 基于 Picocli 的命令行工具，提供环境诊断、题库检查、迁移、开始训练、提交、判题、历史和导出能力 | 覆盖本地、离线和偏开发者的训练工作流 |
| `training-web` | Spring Boot REST API、SSE 判题进度推送、会话管理、Dashboard 与静态资源托管 | 为可视化训练提供稳定服务边界 |
| `training-ui` | Vue 3 + Vite 前端，提供训练工作台、代码编辑、倒计时、题目浏览、历史和报告面板 | 降低训练使用门槛，提升过程反馈效率 |

这样的拆分避免了“判题逻辑只存在于页面或命令中”的重复实现问题。后续新增桌面端、开放 API 或企业端时，能够继续复用 `training-core` 的领域能力。

### 2.2 题库与训练数据建模

题库覆盖机试、口述和项目答辩题，配置层按题型管理题干、标签、难度、参考内容与 starter 代码映射；运行期则将训练数据与只读题库分离，避免训练过程污染题源。

我围绕训练生命周期设计了题目、训练会话、提交记录、判题结果和复习进度等数据模型，并通过 SQLite + Flyway 管理本地数据与版本迁移。数据文件、沙箱目录、导出文件和日志统一放到运行期目录，使题库可升级、运行数据可备份、部署数据可挂载。

数据沉淀后，可以支持以下分析和产品能力：

- 按题型、难度、标签、完成状态查询训练历史；
- 统计正确率、耗时、近期训练频次等基础指标；
- 对失败或未掌握题目进入复习队列，形成间隔复习基础；
- 导出 Markdown/CSV 训练记录，用于个人复盘或向导师同步训练结果。

### 2.3 机试判题与沙箱执行

对于代码题，系统不直接在服务进程中执行用户代码，而是将代码判题抽象为独立的沙箱执行流程。判题服务负责准备训练上下文、触发执行、汇总结果；沙箱负责调用本机工具链完成编译和测试。

当前已支持 JDK 17 + Maven 的 Java 判题，以及 Python + pytest 的题目执行环境；判题过程中通过 SSE 向前端推送进度，减少用户在长时间编译或测试期间的无反馈等待。对于编译失败、测试失败等场景，系统保留诊断信息，帮助用户区分语法问题、环境问题和逻辑错误。

训练用 starter 代码与参考答案、JUnit 测试相互隔离：starter 只提供待完成骨架，参考答案和测试用于判题，不作为训练时直接暴露的答案来源。这既保证了训练真实性，也使题目能够标准化验收。

### 2.4 Web 训练体验与服务治理

Web 端将训练流程组织成完整工作台：题库浏览和会话创建、代码编辑、倒计时、提交与判题进度、训练历史、数据看板和报告导出。后端提供 REST API，并针对耗时判题使用 SSE 进行实时反馈。

在工程化方面，项目还具备以下能力：

- 通过 Trace ID 过滤器串联请求日志，便于定位一次训练或判题请求；
- 对接口提供轻量 API Key 保护，并配合令牌桶限流，适合本地工具或小范围部署；
- 提供环境诊断、启动恢复、题库缓存和 Redis 缓存扩展能力；
- 暴露健康检查与 OpenAPI/Swagger 页面，降低部署排障和接口联调成本。

## 3. 业务模型：从“题库工具”到“训练闭环”

该项目的业务本质是一个能力提升产品，而非单次答题工具。它围绕开发者求职周期设计三个阶段：

| 阶段 | 用户问题 | 产品能力 | 关键产出 |
| --- | --- | --- | --- |
| 诊断 | 不清楚自己与目标岗位的差距 | 基于题型、标签、难度的基础训练与数据看板 | 初始能力画像、薄弱知识点 |
| 训练 | 不知道练什么，无法坚持 | 限时会话、机试/口述/项目答辩多题型训练、即时判题 | 提交记录、得分、耗时、诊断信息 |
| 复盘 | 答错后不复习，知识无法沉淀 | 历史查询、错题队列、复习调度、Markdown/CSV 导出 | 复习任务、个人训练档案 |

从岗位匹配角度，题库可以按 Java 基础、并发与 JVM、Spring 生态、系统设计、算法机试、AI Agent 基础、RAG、工具调用、上下文与记忆管理、项目表达等方向组织。用户选择“Java 转 AI Agent”目标后，产品能够在后续版本中根据其历史错误率、题目重要度和面试周期动态调整训练权重。

## 4. 产品生命周期与演进规划

### 阶段一：MVP——验证训练闭环

先解决“可训练、可记录、可复盘”的最小问题：本地题库、CLI/Web 双入口、训练会话、代码判题、历史记录和训练报告导出。当前项目已经覆盖这一阶段的主要能力，并完成 Docker 化部署方案。

### 阶段二：增长——提升训练效率与留存

重点是让系统从“用户自己挑题”升级为“系统帮助用户安排训练”。具体包括：更细的能力标签、错题权重、基于遗忘曲线的复习调度、训练目标管理，以及按岗位生成的训练计划。衡量指标可关注训练完成率、7/30 日留存、复习完成率和正确率提升。

### 阶段三：智能化——引入 AI Agent 面试官

针对口述题、系统设计题和项目答辩题，可接入大模型评审能力：以评分 Rubric、参考要点和结构化输出约束模型，生成维度化评分、遗漏点和改进建议；再由 Agent 依据用户回答发起多轮追问，模拟真实面试中的深挖过程。

这一阶段的关键不是直接把大模型当“标准答案”，而是建立可解释的评分维度、人工可复核的证据和低置信度兜底机制。例如：事实型知识点优先使用规则校验，开放题使用 LLM 评分并保留评分理由；高风险结论由参考要点或人工复核确认。

### 阶段四：平台化——面向个人与机构交付

个人版可采用“基础题库免费 + 高级训练计划/AI 评审次数增值”的模式；机构版可提供私有化部署、定制题库、班级训练看板、统一评估报告和数据隔离能力。当前项目的本地 SQLite、Docker 数据卷、备份恢复和 API 边界设计，为私有化交付提供了基础。

## 5. 部署与运维设计

项目提供 Docker 化封装和 Linux 部署脚本，支持镜像构建、Compose 编排、数据目录挂载、健康检查、版本发布记录、升级前备份和故障恢复。运行期数据统一独立于镜像和只读题库，升级应用时可以保留用户训练记录；数据库迁移则由 Flyway 管理，保证版本升级过程可控。

部署链路可以概括为：

```text
构建后端与前端产物 → 构建容器镜像 → Compose 启动服务
        ↓                                      ↓
  挂载运行期目录 ← 健康检查 ← 数据库迁移 ← 运行服务
        ↓
训练数据库 / 沙箱文件 / 导出报告 / 发布与备份记录
```

## 6. 项目成果与可量化指标

- 已沉淀 100+ 道 Java、AI Agent 和项目实战方向的结构化训练题，并具备扩展题库的配置化能力；
- 支持机试、口述题、项目答辩等多种训练形式，以及 CLI 与 Web 两种训练入口；
- 支持 Markdown、CSV 格式训练记录导出，方便复盘和外部留档；
- 通过错题记录、历史检索和复习队列，将复盘从“手工找题、手工记录”转为系统化过程。若有真实试用数据，可表述为“错题复盘效率提升约 50%”；
- 完成 Docker 容器化、数据挂载、健康检查、备份恢复等部署能力，在准备好运行环境的情况下可快速完成服务搭建。

## 7. 面试口述版本（约 2 分钟）

我做的是一个面向开发者的结构化面试训练系统，主要解决刷题过程中题目分散、训练没有记录、答错后难以系统复盘的问题。它既支持机试题，也支持口述题和项目答辩题，最终希望把面试准备做成“训练、判题、复盘、复习”的数据闭环。

技术上，我采用 Java 17 的 Maven 多模块架构，把核心能力拆成 `training-core`、`training-cli` 和 `training-web`。核心模块负责题库加载、训练会话、SQLite 持久化、复习队列和代码沙箱；CLI 面向本地和离线训练，Web 端采用 Spring Boot + Vue 3，提供可视化工作台、倒计时、历史记录和数据看板。这样做的好处是训练规则只维护一份，后续无论加桌面端、开放 API 还是机构端，都可以复用领域层能力。

机试判题是项目中相对有挑战的一部分。我没有让用户代码直接跑在 Web 服务进程里，而是通过独立沙箱调用 JDK、Maven 或 pytest 工具链完成编译和测试；后端通过 SSE 将判题进度推到前端，同时保留编译失败和测试失败的诊断信息。训练题中的 starter 代码、参考答案和测试用例也做了隔离，避免训练过程泄露答案。

业务上，我把用户路径设计成先诊断薄弱项，再做限时训练，之后根据错误记录进入复习队列。当前项目已沉淀 100 多道 Java、AI Agent 和项目实战题，支持导出 Markdown 和 CSV 训练报告，也完成了 Docker 化部署、数据挂载、健康检查以及备份恢复。后续我计划接入基于评分 Rubric 的 LLM 评审和多轮追问 Agent，重点覆盖系统设计、项目答辩和 AI Agent 场景题。

## 8. 面试追问准备

### 为什么选择 SQLite，而不是一开始就用 MySQL？

目标用户主要是个人开发者和私有化小规模使用场景，SQLite 零运维、可随应用挂载、便于备份和本地部署，很适合作为 MVP 的数据方案。通过 Flyway 维护迁移脚本，并在 Repository/Service 边界隔离持久化逻辑，后续迁移到 MySQL 或 PostgreSQL 的成本可控；当出现高并发、多用户权限和跨实例共享数据需求时，再引入服务型数据库更合理。

### 代码沙箱的风险如何控制？

当前系统首先将判题执行与 Web 服务逻辑隔离，使用独立运行目录并限制训练代码只在沙箱流程中执行。生产化还应进一步增加容器级隔离、非 root 用户、CPU/内存/进程数/执行时长限制、网络禁用、文件系统白名单和执行审计，不能把本机进程执行视为完整安全沙箱。

### LLM 判题如何避免不稳定或“幻觉”？

不会将 LLM 作为唯一事实来源。客观题和可验证知识点优先采用规则或测试用例；开放题则通过明确评分 Rubric、参考要点、结构化 JSON 输出和评分理由提高一致性。对于低置信度、高影响结果保留人工复核入口，并记录模型版本、提示词版本和评审证据，方便回溯与评估。

### 为什么既做 CLI 又做 Web？

两者服务的用户习惯不同：CLI 更适合开发者在本地快速诊断、批处理、离线训练和脚本集成；Web 更适合可视化答题、进度反馈、历史浏览和训练报告。两种入口复用核心领域层，因此是场景扩展，不是重复建设。
